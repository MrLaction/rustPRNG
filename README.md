# rustPRNG

Generate 40-digit pseudorandom numbers, evaluate their primality, and simulate RSA-OAEP communication using factors generated by the project.

The application has two independent workflows:

- **Number experiments:** compare three generators, produce 40-digit numbers, and count probable primes.
- **Cryptography:** generate two 1024-bit probable primes, construct a 2048-bit RSA key pair from those exact factors, and transmit a short encrypted message through an in-memory channel.

Both workflows use our Miller-Rabin implementation with 32 randomized rounds. Accepted values are **probable primes, not proven primes**. No definitive primality-proving stage is included.

## Getting started

Install Rust and Cargo, then run:

```bash
git clone https://github.com/MrLaction/rustPRNG.git
cd rustPRNG
cargo test --release
cargo run --release
```

Use a recent stable Rust toolchain compatible with edition 2024. Cargo downloads the required dependencies during the first build. No Python or PARI/GP installation is needed for the Rust application.

Use `cargo run` during development and `cargo run --release` for performance measurements. Release mode is also recommended for tests that generate large RSA factors.

## Using the program

The initial menu separates the original experiment from the cryptography extension:

```text
Main menu
1. Number generation and primality experiments
2. Cryptography
0. Exit
```

### Number generation and primality experiments

Select `1` in the main menu. The program then asks for the algorithm, its parameters, the operating mode, and the number of values to generate.

| Option | Algorithm | Parameters |
| --- | --- | --- |
| `1` | SHA-256 Counter | `seed`, `salt` |
| `2` | ChaCha20 | `key_seed`, `nonce_seed` |
| `3` | Blum Blum Shub | `p`, `q`, `seed` |

The two operating modes are:

- **Generate numbers:** print the requested numbers without testing primality.
- **Generate numbers and count probable primes:** generate and classify the entire batch, then print every result and a summary.

Example input for the SHA-256 experiment:

```text
Main menu: 1
Algorithm: 1
Seed: 109281
Salt: 102939
Mode: 2
Count: 100000
```

Enter each value when prompted. The labels above describe the input order.

In the second mode, each output line ends with `probably prime` or `not prime`. Results are stored in generation order and printed only after processing finishes. The program does not regenerate or retest the numbers when printing them.

### Cryptography

Select `2` in the main menu. The program:

1. Initializes our ChaCha20 generator using randomness from the operating system.
2. Searches for two suitable 1024-bit probable primes.
3. Constructs the receiver's RSA key pair from those factors.
4. Displays the public modulus and exponent.
5. Requests one line of text, up to **190 UTF-8 bytes**.
6. Encrypts the text with RSA-OAEP and SHA-256.
7. Passes the ciphertext through a simulated channel.
8. Decrypts it and checks exact equality with the original message.

Spaces are preserved; the input line ending is removed. Non-ASCII characters can occupy multiple bytes. Oversized input is rejected and requested again.

Each execution generates a fresh key pair. The interactive simulation sends one message per execution and does not save keys or open network connections.

## Algorithms

### SHA-256 Counter

Each block hashes a domain identifier, length-prefixed seed and salt encodings, and an incrementing counter. The project defines this construction; the `sha2` crate provides SHA-256.

$$
B_i = \operatorname{SHA256}(D \parallel L(S) \parallel S \parallel L(T) \parallel T \parallel C_i)
$$

Here, $S$ and $T$ are the big-endian seed and salt bytes, $L$ encodes their lengths as 64-bit big-endian integers, $C_i$ is the 64-bit big-endian counter, and $\parallel$ means byte concatenation. The domain identifier $D$ distinguishes this construction. Each digest supplies 32 bytes.

The counter starts at zero. Unused bytes from a hash block are discarded by the current implementation. Reproducing the sequence therefore requires the same parameters and the same pattern of byte requests, as provided by the shared number sampler.

### ChaCha20

SHA-256 derives a 32-byte key and a 12-byte nonce from the two numeric input parameters, using separate domain identifiers. The `chacha20` crate produces the keystream and retains its position between calls.

ChaCha20 mixes a state containing constants, the key, a block counter, and the nonce through addition modulo $2^{32}$, XOR, and bit rotations. Our wrapper applies the keystream to zero-filled buffers, yielding the pseudorandom bytes themselves.

The experiment uses user-provided numeric seeds for reproducibility. The cryptography workflow reuses this wrapper with fresh system-generated seeds.

### Blum Blum Shub

BBS is implemented directly in the project. It initializes a state and repeatedly squares it modulo the product of two primes:

$$
M=pq,\qquad x_0=\mathrm{seed}^2\bmod M,\qquad x_{i+1}=x_i^2\bmod M
$$

Each step emits the least significant bit of the updated state. Eight bits form one output byte.

The program requires distinct probable primes `p` and `q`, both congruent to `3` modulo `4`. It also checks `1 < seed < p * q`, coprimality of the seed and modulus, and rejection of the fixed initial state `1`.

Small parameters can produce short cycles. Having 40 output digits alone does not guarantee a long period or good statistical properties.

## Number conversion and primality

All three generators feed the same sampler:

1. Request 17 bytes and mask off the top three bits, leaving 133 bits.
2. Interpret the bytes as a non-negative integer `r`.
3. Accept only if `r < 9 * 10^39`; otherwise retry.
4. Return `10^39 + r`.

Every accepted result is in `[10^39, 10^40)` and has exactly 40 decimal digits. Rejection sampling avoids modulo bias when supplied with uniform bits. The program stops with an error after 1,024 consecutive rejected candidates.

### Miller-Rabin

The primality module handles small values and divisibility by the primes from 2 through 37 before applying Miller-Rabin. For an odd candidate $N>37$, it writes:

$$
N-1=d\,2^s,\qquad d\text{ odd}.
$$

Each round samples a base $a$ uniformly from $[2,N-2]$ and computes $x=a^d\bmod N$. The candidate passes that round if:

$$
a^d\equiv1\pmod N
\quad\text{or}\quad
a^{d2^r}\equiv-1\pmod N\text{ for some }0\le r<s.
$$

Repeated modular squaring checks the second condition. Failure establishes compositeness; passing all 32 rounds yields a probable prime.

For a fixed odd composite, independent uniform bases give a false-acceptance bound of $4^{-32}=2^{-64}$. This is not a posterior probability that any particular accepted candidate is composite, nor a bound for the entire application.

| Classification | Meaning |
| --- | --- |
| `not prime` | The test established that the number is not prime. |
| `probably prime` | The number passed all configured checks, but no primality proof was produced. |

The decision logic is implemented in `src/prime.rs`. `num-bigint` supplies large-integer arithmetic and modular exponentiation; `rand` supplies the bytes used to choose test bases.

Generated sequences are reproducible for fixed generator settings. Miller-Rabin bases are sampled separately on each run, so execution paths and timing may vary. A false positive remains theoretically possible.

## Cryptography and mathematical foundations

### Generating RSA factors

The cryptography workflow generates **new, larger factors**. It does not import the original 40-digit experiment results or a list previously checked in PARI/GP.

`OsRng` supplies 64 bytes, split into two seeds for our ChaCha20 wrapper. Each candidate uses 128 generated bytes. The two highest bits and the lowest bit are set to one, making the candidate odd and restricting it to:

$$
3\cdot2^{1022}\le p,q<2^{1024}.
$$

Consequently:

$$
2^{2047}<9\cdot2^{2044}\le pq<2^{2048},
$$

so the product has exactly 2048 bits. Each factor has 309 decimal digits. The upper-bit restriction intentionally samples a subset of the 1024-bit integers.

Before accepting the pair, the search enforces:

- Each candidate passes the existing 32-round Miller-Rabin test.
- Neither candidate is congruent to 1 modulo the public exponent, $e=65537$.
- The factors satisfy $|p-q|>2^{924}$, which also excludes equality.

Since $e$ is prime, the exponent condition ensures it is coprime to both $p-1$ and $q-1$.

The search stops with an error after 100,000 generated candidates if no pair is found. The candidate counter includes candidates rejected before Miller-Rabin.

### Constructing the keys from our factors

For distinct primes $p$ and $q$, RSA uses:

$$
n=pq,\qquad \lambda(n)=\operatorname{lcm}(p-1,q-1).
$$

With $\gcd(e,\lambda(n))=1$, a modular inverse exists:

$$
d=e^{-1}\bmod\lambda(n),\qquad ed\equiv1\pmod{\lambda(n)}.
$$

The public key is $(n,e)$. The receiver holds the private exponent $d$ and the factors needed by its private-key representation.

`keys.rs` converts our `num_bigint::BigUint` values to the RSA crate's integer type through exact big-endian byte encodings.

`RsaPrivateKey::from_p_q` constructs the key from those supplied values; it does not generate replacement factors. The tests verify that the private key retains the original factors and that its modulus equals their product.

Key construction checks algebraic consistency. It does **not** turn the probable-prime classification into a primality proof. The following correctness argument assumes the accepted factors are actually prime.

### Why RSA recovers the message

For an encoded integer $m$ satisfying $0\le m<n$, the core operations are:

$$
c=m^e\bmod n,\qquad m'=c^d\bmod n.
$$

Because $ed\equiv1\pmod{p-1}$, Fermat's little theorem gives $m^{ed}\equiv m\pmod p$ when $m$ is not divisible by $p$. When it is divisible by $p$, both sides are zero modulo $p$. The same reasoning applies modulo $q$.

The Chinese remainder theorem then gives $m^{ed}\equiv m\pmod{pq}$. Since the recovered representative is in $[0,n)$, it equals the original representative.

### OAEP, SHA-256, and the message limit

The application uses **RSA-OAEP**, rather than applying RSA directly to raw text.

OAEP encodes the UTF-8 bytes using a fresh random seed, SHA-256, and mask generation before the modular operation. Repeated encryption of the same message under one key is randomized. Here, $m$ in the RSA equations represents the OAEP-encoded block.

For modulus size $k$ bytes and hash output size $h$, the maximum message length is:

$$
\mathrm{mLen}\le k-2h-2=256-2(32)-2=190\text{ bytes}.
$$

Each ciphertext occupies 256 bytes, displayed as 512 hexadecimal characters. Hexadecimal is only a display format.

The receiver performs blinded RSA decryption, validates the OAEP encoding, and converts the recovered bytes back to UTF-8.

OAEP is specified in [RFC 8017, Section 7.1](https://www.rfc-editor.org/rfc/rfc8017.html#section-7.1).

### Transmitter, channel, and receiver

| Component | Information held | Responsibility |
| --- | --- | --- |
| Transmitter | Receiver's public key and outgoing plaintext | Enforce the byte limit and encrypt with OAEP. |
| Channel | Ciphertext packets in a `VecDeque` | Deliver packets in first-in, first-out order. |
| Receiver | Private key and incoming ciphertext | Decrypt and reconstruct the UTF-8 message. |
| Simulation coordinator | Original and recovered messages | Display the demonstration and compare both values. |

These are logical components in one process, not separate machines or security-isolated processes. The channel receives neither keys nor plaintext. The coordinator knows both texts for verification and displays them in the console.

`Exact message match: yes` reports a local equality check. It does not authenticate the sender. Anyone with the public key can create a new valid ciphertext; the program includes no signatures, trusted public-key distribution, or replay protection.

### Implementation responsibilities

| Responsibility | Implementation |
| --- | --- |
| Candidate generation and RSA-factor selection | Project code, reusing our ChaCha20 wrapper. |
| Probable-prime decision | Project Miller-Rabin implementation. |
| Large-integer arithmetic and modular powers | `num-bigint` and the RSA crate's integer backend. |
| SHA-256 and ChaCha20 primitives | `sha2` and `chacha20`. |
| Operating-system randomness | `rand::rngs::OsRng`. |
| RSA key construction, OAEP, and blinded decryption | `rsa`. |
| Communication simulation and verification | Project transmitter, channel, receiver, and coordinator. |

## Testing and project structure

```bash
cargo test --release
```

The current version passed **16 tests** on the development machine. The original 14 tests cover 40-digit output, reproducibility, parameter changes, BBS validation and reference bytes, buffer handling, primality cases, and preservation of experiment order.

The two cryptography tests additionally check:

- Preservation of the generated RSA factors and their product.
- The private/public exponent relation modulo each factor minus one.
- OAEP round trips for empty input, Unicode, and the 190-byte boundary.
- Rejection of oversized input, including a multibyte UTF-8 example.
- Rejection of an invalid all-zero ciphertext and a truncated packet.
- Channel ordering, exact whitespace preservation, and an empty receive queue.

These tests verify specific behaviors; they are not a security audit or primality certificates.

## Scope

Users control the technique, initial parameters, operating mode, and batch size. Input validation constrains configurations; reproducible output and summaries make the system's behavior observable.

The cryptography workflow extends that experiment into an educational communication simulation. Its algorithm and key size are fixed; it automatically selects fresh factors and exposes the public key, timings, ciphertext, and recovery result.

Current boundaries are:

- Probable-prime testing only; no integrated PARI/GP validation or certificates.
- One interactive message of at most 190 UTF-8 bytes; no long-message splitting or hybrid encryption.
- In-memory communication; no sockets, separate hosts, or persistent keys.
- No sender authentication, signatures, or replay protection.
- Sequential execution; no parallel processing or persistent caches.
- Batch memory usage grows with the requested count because classified results are retained until printing.

The project demonstrates the mathematics and data flow. It has not been audited or validated as a production cryptographic system. Selecting a 2048-bit modulus and OAEP alone does not establish the security of the entire implementation.
